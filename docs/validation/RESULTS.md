# WP-10 Validation Results

**Data source: 100% SYNTHETIC.** No real cached NIFTY candle data exists anywhere in this
repo, and fetching real history requires a live Angel One broker session, which is out of
scope/forbidden for this task (no credentials, no `-live`). Every number below comes from
`docs/validation/data/nifty_synthetic_5min.csv` — a fabricated ~2.5-year, 5-minute OHLCV
series generated by `docs/validation/gen_synthetic_data.py` (geometric random walk with
regime-dependent drift/vol: range-bound, uptrend, a sharp gap-down shock, volatile
recovery, range-bound, uptrend, mixed — see that file's header comment for the exact
schedule). **These results demonstrate that the walk-forward harness and the WP-7 backtest
engine work end to end. They are NOT evidence of a real trading edge or its absence in the
actual NIFTY market.** Treat every table below as "how would this strategy have behaved on
a market that moved like this," not "how NIFTY will behave."

Options are priced with the WP-7 Black-Scholes engine at a **constant annualized IV**
(default 12%, no smile/skew/term-structure, no day-to-day IV changes) — inherited
verbatim from `docs/reports/WP-7-REPORT.md`'s documented v1 limitation. This matters a lot
for the results below: it means every short-premium strategy here is graded with **zero
vega/IV-crush risk modeled** — a real short straddle can be crushed by an IV spike even if
spot barely moves; this backtest cannot show that failure mode at all. Any strategy that
"passes" here has not been tested against that risk.

## Method

- Binary: `docs/validation/bin/backtest.exe`, built via `go build -o docs/validation/bin/backtest.exe ./cmd/backtest` from `go-engine/` (unmodified `cmd/backtest/main.go`; no source edited for this WP).
- Data: `docs/validation/data/nifty_synthetic_5min.csv`, 2024-01-01 → 2026-06-30, 48,900 five-minute bars, IST session hours, weekdays only (Indian market holidays not modeled — a known simplification).
- Walk-forward: 2024-01 → 2024-06 treated as the "train" burn-in and **not scored** (see "Why 'train' does nothing" below). 24 rolling **1-calendar-month** out-of-sample test windows from 2024-07 through 2026-06, run independently per window per strategy, at the strategy's compiled-in default parameters and the backtest's default config (`-iv 0.12 -dte 7 -strikestep 50 -lotsize 75`).
- Driver: `docs/validation/run_walkforward.py` shells out to the exe once per (strategy, window), parses the printed report, and writes `docs/validation/out/walkforward_windows.csv` (168 rows = 7 strategies × 24 windows) and `docs/validation/out/sensitivity_grid.csv` (48 rows, see Sensitivity below).
- Aggregation: `docs/validation/summarize.py` pools all 24 windows per strategy into `docs/validation/out/strategy_summary.csv` (trades, pooled win rate, pooled profit factor, per-trade expectancy, worst single window/day).

**Representative command** (one per strategy; every strategy was run over all 24 windows with the same flags, only `-strategy`/`-from`/`-to` varied):
```
docs/validation/bin/backtest.exe -strategy short_straddle -symbol NIFTY \
  -csv docs/validation/data/nifty_synthetic_5min.csv \
  -from 2024-07-01 -to 2024-07-31 -lotsize 75 -iv 0.12 -dte 7 -strikestep 50
```

### Why "train" does nothing here (blocker, not hidden)

The WP-10 brief's "6-month train / 1-month test" template assumes strategies have
parameters that get *fit* on the train window and then evaluated OOS on the test window.
**These strategies have no fitting step.** Every strategy in `internal/strategy/*.go` uses
fixed, compiled-in constants (e.g. `NewIronFlyStrategy()` hardcodes `WingWidth: 200,
RSILower: 45, RSIUpper: 55`) with no CLI flag or config file to change them per run. So
there is nothing to "train" — the first 6 months of data are burned but not used for
anything. What the walk-forward protocol actually validates here is **regime robustness**
(does performance hold up across trending/ranging/shock months), not
parameter-generalization. This is stated plainly rather than fabricating a train step that
doesn't exist.

**2x-cost method note:** the engine's cost model is purely subtractive
(`NetPnL = GrossPnL - Charges`; verified in `internal/backtest/engine.go`/`report.go` —
charges never feed back into fill price, stop triggers, or trade count). Doubling every
charge is therefore algebraically exact as `NetPnL' = NetPnL - Charges`, computed directly
from the already-reported columns — no re-run needed, no approximation, and no strategy
parameter or code was touched to do it. This recomputes **expectancy** exactly; it does
**not** recompute pooled profit factor at 2x cost (that needs the per-trade ledger to
reclassify individual near-breakeven trades from win to loss, which `report.String()`
doesn't expose) — the WP-10 gate only requires positive expectancy at 2x cost, which is
what's reported.

## Go/no-go against the WP-10 gates

Gates: **(a)** pooled OOS profit factor > 1.3, **(b)** max drawdown < 15% of deployed
margin/capital, **(c)** positive expectancy after doubling modeled costs.

Gate (b) cannot be graded precisely: **the backtest models no margin at all** — no SPAN,
no exposure margin, no broker margin API call. `Config`/`engine.go` track P&L and a
peak-to-trough equity drawdown in absolute rupees, nothing else. For the naked/hedged
short-premium strategies (nine_twenty, short_straddle, iron_fly) real deployed capital is
whatever margin the broker actually blocks for a 1-lot NIFTY option sale — commonly on the
order of ₹1.5–2 lakh per lot for a naked short as of recent NSE SPAN+exposure rules, but
this is a rough outside estimate, **not** sourced from `internal/broker`'s margin endpoint
(A-6, unused by the backtest), so it is shown only as a sanity-check ratio, not a pass/fail
input. For the directional strategies (ema_crossover, momentum, rsi_reversal, sniper) risk
per trade is capped at the premium paid (they only ever `LegBuy` a synthetic ATM
CE/PE — confirmed in `internal/backtest/engine.go`'s `openDirectional`), so "deployed
capital" is much smaller and the ratio is less alarming by construction.

## Findings worth flagging beyond the raw numbers

1. **`sniper` cannot be meaningfully backtested via `internal/backtest` as currently
   wired — 0 trades across all 24 windows, all regimes.** Root cause (traced through
   `internal/backtest/engine.go:276-288` and `internal/strategy/sniper.go`): `sniper.go`'s
   `Evaluate` has a documented "candle-mode" fast path for backtest-style callers, gated on
   `len(ctx.Prices) == 0 && len(ctx.Candles) > 0`. But `engine.go`'s per-candle loop
   **always** populates `ctx.Prices` when flat (`ctx.Prices = closesOf(history)`), so that
   condition is never true, and every call falls through to `sniper.go`'s live
   tick-aggregation path instead. That path treats each single incoming price as one
   "tick," rebuilding its own candle from a single point (`Open: price, High: price, Low:
   price, Close: price`) every call — a zero-range doji, every time, because it only ever
   sees one price per bucket in this driving pattern. `IsHammer`/`IsBullishEngulfing`/
   `IsShootingStar`/`IsBearishEngulfing` all require real intra-candle range/body, which a
   zero-range candle can never have — so the entry logic can structurally never fire. This
   is an **integration gap between WP-6's sniper contract note and WP-7/WP-9's engine
   wiring**, not evidence about the strategy's real-world edge one way or the other. Per
   this WP's file-ownership constraint (docs/validation/ only), it is reported here rather
   than fixed; whoever owns `internal/backtest/engine.go` and `internal/strategy/sniper.go`
   should either feed sniper an empty `Prices` with real `Candles` when flat, or change
   sniper's mode-detection to something engine-agnostic.
2. **`iron_fly` and `short_straddle` both gate entry AND exit off a fast RSI(14) computed
   on 5-min bars (`RSILower`/`RSIUpper` 45–55)**, which on a noisy random-walk-like price
   series crosses in and out of a 10-point-wide neutral band very often — 53 to 77 entries
   per *month* for iron_fly across all 24 windows, i.e. several a day, every regime,
   including the calm range-bound months (2025-03..2025-08) where a wider hold should have
   let theta actually accrue. A 4-leg iron fly charges 8 orders (entry+exit × 4 legs) worth
   of statutory charges plus spread cost every round trip; against a holding period this
   short relative to the 7-day DTE the option is priced for, transaction costs dominate
   whatever theta/premium was captured almost every single time — pooled win rate is
   3.02% for iron_fly and 18.68% for short_straddle. This is the audit's §8.2 warning
   ("any strategy trading every 5 minutes is structurally handicapped") **empirically
   reproduced**, not a new bug — but it does mean the reported iron_fly numbers are as much
   an artifact of the exit-gating choice (RSI leaving 45-55) as of the underlying being
   short options.
3. **nine_twenty loses in 24/24 windows, including the calm range-bound months** — not
   just the modeled Oct-2024 shock. It does have a real premium stop now (WP-6's CR-14 fix,
   `StopMultiplier: 1.4`), unlike the pre-remediation code, but a 40%-of-entry-premium
   stop is evidently still far too loose against 5-min-granularity Black-Scholes repricing
   under this vol regime — losses accumulate steadily even without a single trend day.

## Parameter/config sensitivity (the CLI-exposed knobs)

**Blocker, stated plainly:** the CLI (`cmd/backtest/main.go`) exposes no flags for
strategy-*internal* parameters — RSI thresholds, EMA periods, iron_fly's `WingWidth`,
nine_twenty's `StopMultiplier`, etc. are all hardcoded in each strategy's `New*()`
constructor (see `internal/strategy/{iron_fly,short_straddle,nine_twenty,ema_crossover,
rsi_reversal,momentum,sniper}.go`). Adding such flags would require editing
`cmd/backtest/main.go` and/or the strategy files, which this WP's hard constraint
(docs/validation/ only, no source edits) forbids. **A true RSI-threshold/EMA-period/
wing-width sensitivity sweep was therefore not run** — this is a real gap, not an oversight,
and whoever picks up strategy tuning next needs CLI/config support for it first.

What the CLI *does* expose and what was swept instead (`docs/validation/out/sensitivity_grid.csv`,
48 rows: 4 strategies × 4 IV levels × 3 DTE settings, fixed window 2025-09..2025-11,
an uptrend regime):

**This is the single most important finding in this report.** short_straddle's result
flips from a clear loser to a apparent winner purely by turning the assumed constant IV
dial up from 8% to 25% — with *no change to the market data or the strategy logic at
all*. That is not a real edge appearing; it is the WP-7-documented v1 limitation
(`internal/backtest/bs.go`: "IV is a single constant per run... reconstructing a historical
per-strike IV series is explicitly not implemented") manifesting exactly as a naive reader
should worry it would: **a higher assumed constant IV means the strategy is modeled as
selling richer premium upfront, with the model never allowing that IV to itself move
against the position (no vega risk, no IV-crush-in-reverse).** Any apparently-positive
straddle/iron-fly/nine_twenty result in this report or any future one **must** be checked
against which IV assumption produced it before being taken seriously — and none of them
should be taken as evidence of a real edge without a real historical IV series, which does
not exist in this codebase (Phase 3 future work per WP-7). ema_crossover shows the same
sensitivity in reverse (a long-option/long-premium/directional strategy does *worse* at
higher assumed IV, since it pays more for the same option) — directionally consistent with
long-vega/short-vega intuition, which is at least a sanity check that the BS repricing is
behaving the way real option pricing should, even though the absolute levels aren't
trustworthy.

DTE sensitivity (same grid): short-dated (3-day) legs consistently outperform 14-day legs
for every option-selling strategy at every IV level tested — again a mechanical consequence
of less BS time-value to decay against a short hold, not a claim that real weekly options
in the 3-14 DTE band behave this way.

## What would be needed to turn this into a real edge test

1. Real historical NIFTY 5-min index candles, ≥2-3 years, spanning at least one real trend
   year and one real range-bound year (2024/2025 per the audit) — requires a live broker
   session this task cannot use.
2. Real historical option-chain premium data (not BS-reconstructed from a constant IV) for
   the option-selling strategies, or at minimum a reconstructed historical IV series
   (Phase 3 per WP-7's report) so vega/IV-crush risk actually shows up in the backtest.
3. CLI or config support for strategy-internal parameter sweeps (RSI thresholds, EMA
   periods, wing width, stop multipliers) — currently hardcoded per strategy, no flag
   exists, and this WP cannot add one without violating its own file-ownership
   constraint.
4. A margin model (broker margin API, endpoint A-6) so the drawdown gate can be graded
   against real deployed capital instead of a rough outside estimate.
5. A fix for the `sniper` candle-mode integration gap (Finding 1) before it can be
   evaluated at all.
